1. PASTE AFTER GATE 4, as a new heading "GATE 4.5 - CLAIM THE SLOT (cloud-clone mode only)"
=====================================================================

GATE 4.5 - CLAIM THE SLOT (cloud-clone mode only). Skip this gate entirely unless Gate 2 took the cloud-clone path. It runs only after Gate 4 has passed, including Gate 4's compatible-executor continuation, and before Gate 6 reads any broker history. Gate 4 sees orders at the broker; this gate sees other cloud runs that have not ordered yet, so it closes the window between two containers starting the same slot. From the repo root run: `python3 -m scripts.evidence_publish claim --evidence-root "$DCA_CRON_TRACKING_ROOT" --remote "$DCA_EVIDENCE_REMOTE" --trading-day <today in America/New_York, YYYY-MM-DD> --slot <this slot id, e.g. 0935> --claimant <slot>-<Gate 1's ET instant as YYYYMMDDTHHMMSS>`. The claimant is built only from the slot id and that instant; it never contains the account number, the remote URL or anything else (a claimant holding the account number is refused with exit 4). Give it at most 180 seconds and never retry it: the remote rejecting a non-fast-forward push IS the mutex, and any existing claim is refused even for the same claimant so that a scheduler retry cannot place a second set of orders. Exit 0 means this run owns the slot: record `SLOT_OWNED=yes` and RESUME AT GATE 5 (signal generation) -- the claim sits after Gate 4 but Gate 5 has not yet run, so do not skip ahead to Gate 6. Exit 5 means another run already owns it: abort `Failing gate: Gate 4` with "slot already claimed by another run" and place nothing. Exit 6, exit 4, a timeout, or any other result aborts `Failing gate: Gate 4` with "slot claim could not be confirmed" (fail closed: an unproven claim is no claim). OWNERSHIP RULE: only a run that saw claim exit 0 (`SLOT_OWNED=yes`) may finalize into, modify or publish the canonical slot record (`<day>_<slot>` outcome, report, state marked finalized_by=scripts.finalize_run_evidence). Any run without confirmed ownership -- claim exit 5, 4, 6, a timeout, OR an abort BEFORE the claim was attempted (for example Gate 4's order-history fetch failing after Gate 2's preflight pulled the winner's evidence) -- must NOT run finalize against the canonical slot directory and must NOT run the PUBLISH step: finalize rebuilds a finalized state and would replace the winner's outcome/report, and publish would push that over it as a normal update. Instead write that run's abort artifacts and alert under an attempt-scoped directory, `$DCA_CRON_TRACKING_ROOT/unowned_attempts/<day>_<slot>_<claimant>/` (claimant = the slot id plus Gate 1's ET instant), pass that directory to finalize_run_evidence as its output root, and keep it local; the alert still goes out on every channel and names the attempt directory. Robinhood's own ref_id remains the second line of defence; whether the broker rejects a repeated ref_id is not verified, so this gate is not optional and does not relax any other gate.

2. PASTE INTO GATE 9, as a new step directly after the finalize_run_evidence block (after the sentence ending "...is what this command produces, not a second instruction to write those files yourself.") and BEFORE the three-channel notification
=====================================================================

PUBLISH THE EVIDENCE (cloud-clone mode only; skip on a Mac or bridge run, and skip when Gate 2 found no repo). A cloud container is thrown away after this fire, so evidence that is not pushed is lost, and the next slot's preflight cannot see this one. Run it on EVERY OWNED outcome (`SLOT_OWNED=yes`) once finalize_run_evidence has exited 0 or 1: orders placed, zero orders, END_SILENTLY, and every abort after the claim alike. A run without confirmed ownership skips this step entirely (OWNERSHIP RULE in Gate 4.5). If finalize exited 2 nothing was written, so there is nothing to publish; say so in the alert. Before finalizing, add `--code-version-json '{"git_sha":"<the 40-character SHA from Gate 2's PREFLIGHT_OK line>","pinned_by":"DCA_PINNED_SHA"}'` to the finalize command, so the run's record names the release that produced it (the command refuses a SHA that is not $DCA_PINNED_SHA). Then, from the repo root: `python3 -m scripts.evidence_publish publish --evidence-root "$DCA_CRON_TRACKING_ROOT" --remote "$DCA_EVIDENCE_REMOTE" --trading-day <YYYY-MM-DD> --slot <this slot id> --code-sha "$DCA_PINNED_SHA"`. Give it at most 240 seconds; do not run it a second time in this session. Exit 0: published; continue to the notification. Exit 3 (push_failed): the artifacts are intact and committed locally and a marker was left at `evidence_push_failed/<day>_<slot>.json`; add the returned `alert_text` to this run's alert and SEND it by email as well as on the other channels (it carries the SHA, slot, orders, tickers, dollars and order IDs, which is why it goes only to the private channels and never into a repo file that is committed). Exit 4 (refused_secret): nothing was pushed; the output names only relative paths. Alert with those paths and say the account number was found in the evidence; never print the number. Exit 7 (refused_provenance): nothing was pushed; alert that the code SHA did not match the pin. A publish failure NEVER changes what was placed and NEVER justifies re-running Gate 7; it is an evidence failure, reported like a finalize failure, with the failing step named as "evidence publish". If publish and the run's own outcome both warrant an alert, send ONE alert covering both.

3. OPEN DECISIONS FOR THE OPERATOR
=====================================================================

- Unowned runs (section 1, OWNERSHIP RULE). Their abort evidence is written to an attempt-scoped local directory and never published, so it is lost with the container; the alert still carries it. Publishing it under a distinct remote directory needs a code change in evidence_publish, not a prompt change.
- Publish before notify (section 2). It delays the abort alert by up to 240 seconds. The alternative, notifying first and publishing after, gets the alert out sooner but cannot fold a publish failure into the same alert. I chose publish first because the alert is the only place a failed push is reported.
- Gate numbering: "4.5" avoids renumbering Gate 5 to 9, which other tools key on (scripts/alert_digest.py buckets on the `Failing gate: Gate N` token). I used `Failing gate: Gate 4` for claim aborts for the same reason, since the claim is the sole-executor interlock's cloud half. If you want it counted separately, it needs a new bucket in alert_digest, which is a code change.
- --code-version-json deliberately omits "tag": the docs list it as optional and I do not know your live-YYYYMMDD-N tag at run time. Add it only if the run environment carries the tag.
- Not verified: none of this has been run against a real evidence repo. Run cloud-clone-dry-run-trial.draft.txt first, then a trial that actually exercises claim and publish against a scratch evidence repo, before touching a live prompt. The claim command accepts only roster slots, so the trial must use a real slot id against the scratch repo (never the real evidence repo) on a day with no live run of that slot.
