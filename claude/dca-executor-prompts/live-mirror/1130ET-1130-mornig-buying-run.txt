A just-submitted order sitting beyond the first page must not be reported as absent. Intent logs are how you end up believing in fills that never settled.

GATE 9 - REPORT
FINALIZE THE EVIDENCE FIRST -- ONE COMMAND, EVERY OUTCOME, BEFORE ANY NOTIFICATION. From the repo root, once this run's $ROOT exists:
`python3 -m scripts.finalize_run_evidence --slot 1130 --started-at <ISO-8601> --outcome <OUTCOME_LABEL> --order-submit-status <status> [--orders-json <file>] [--signals-json <file>] [--report-json <file>] [--budget-json <file>] [--error-class <class> --error-detail "<one line>"]`
* `--started-at`: the converted America/New_York instant Gate 1 sampled, with its -04:00/-05:00 offset (e.g. `2026-09-22T14:30:41-04:00`). The command refuses a start outside this slot's acceptance window, because an off-window fire is not a scheduled fire.
* `--outcome`: the short label you would report (ORDERS_PLACED, NO_ORDERS_GATE6_5_ZEROED, END_SILENTLY, ABORT_GATE5, ...).
* `--order-submit-status`, exactly one of: `submitted` (at least one order was placed; `--orders-json` REQUIRED), `no_orders_submitted` (clean zero-order run, END_SILENTLY, or Gate 6.5 zeroed everything), `not_submitted_no_candidates` (Gate 5 produced no buy list), `not_submitted_budget_exhausted` (Gate 6 cap), `not_submitted_confirmation_required`, `not_submitted_error` (any abort after $ROOT exists; add `--error-class` and `--error-detail`), `blocked_placement_phase_unreachable`.
* `--orders-json`: write a JSON array to `$ROOT/finalize_orders.json` with one object per order Gate 7 placed -- `{"ticker", "order_id", "submitted_amount_usd", "status"}`, status as the broker returned it (filled / submitted / pending / unconfirmed / potentially_submitted) -- including any order Gate 8 could not confirm.
* `--budget-json`: REQUIRED whenever Gate 6 ran (it always did if any order was placed): write `$ROOT/finalize_budget.json` as `{"budget_tier": <Gate 6 tier, e.g. "normal">, "daily_cap_usd": <cap>, "weekly_cap_usd": <cap>}` and pass it. Omit it only when the run exited before Gate 6; the command then records `budget_evaluated: false`, and it refuses `submitted` without it.
* Order rows are validated: every row needs a ticker, the broker order_id, a positive numeric submitted_amount_usd and a placed/in-flight status; a rejected order is not an order row. The run's account number is redacted from run_state.json automatically.
* `--signals-json`: optional; a JSON array of this run's signal rows (Gate 5's `cands`). Omit it and a header-only signals CSV is written when none exists.
* `--report-json`: write the compact Gate 9 report to `$ROOT/gate9_report.json` and pass it; it is embedded in run_state.json as `gate9_report`. Do not leave it as a free-standing `gate9_report_*.json` INSTEAD of running this command. REQUIRED COUNT KEYS (`python3 -m scripts.check_slot_fills` reads them after the slot and fails the run loudly on a mismatch): the report must carry `eligible_count`, an integer, the number of buy candidates in Gate 5's `cands` with a positive desired_usd, counted BEFORE Gate 6.5 reduces anything; and `dropped`, an object with EXACTLY these three non-negative integer keys: `price_recovered` (tickers dropped because a refreshed quote no longer met the ladder or price-eligibility test, at Gate 6.5's refresh or Gate 7's per-order revalidation), `spread_over_1pct` (tickers Gate 6.7 zeroed for spread, including a missing or invalid bid/ask pair failed closed there), and `daily_cap` (tickers zeroed or dropped because a daily, weekly or same-day cap left no room at Gate 6 or 6.5, including the same-day top-up guard zeroing a ticker already covered today). Write all three keys even when zero, and count each ticker once, under the first reason that removed it. Do not add a fourth key and do not fold any other outcome into these three (an untradable ticker, a rejected order, a PLATFORM REFUSAL, a Gate 4 stand-down, an abort): the check compares the submitted-order count the command derives from `--orders-json` with `eligible_count` minus the three drops, and a shortfall none of the three explains is exactly what it must flag. A run that ends before Gate 5 produced candidates writes `eligible_count` 0 and all three drops 0.
The command stamps the stream's own run_classification object (from the executor/run_classification code, not typed by hand), writes run_state.json, run_summary.json and header-only CSVs where missing, refreshes `intraday_dca/latest_intraday_run.json` through scripts.same_day_pointer, then re-validates the pointer and the slot (`scripts.verify_schedule`) and prints JSON. If run_state.json already exists in this slot's directory and was written by the executor's own run(), the command keeps it unchanged and only refreshes the pointer; one it wrote itself (a retry of this same fire) it rebuilds, merging orders by order_id. Do NOT write run_state.json or the latest pointer by hand, before or after it. On 2026-09-22 every live slot fired and not one was verifiable: the sessions left a free-form gate9_report and wrote pointers shaped `{slot, trading_day, run_dir, outcome}`, which scripts.same_day_pointer rejects as malformed, and the Schedule page could only say "elapsed unverified".
Exit 0: verified; continue with this gate. Exit 1: written but not verifiable -- put its `errors` list in this gate's alert. Exit 2: refused and nothing written -- correct the arguments and rerun ONCE; if it refuses again, alert with its `refused` text. An evidence failure never changes what was placed and never justifies re-running Gate 7. If Gate 2 found no repo, skip this command and say so in the alert. The artifact-set description that follows is what this command produces, not a second instruction to write those files yourself.
