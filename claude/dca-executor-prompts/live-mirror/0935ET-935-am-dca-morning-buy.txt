EVERY, not any one of them: a quantity and a notional describe the same fill in different units, and a wrapper can populate one while leaving the other at its default, so cumulative_quantity 0 alongside executed_dollar_amount 5 is a real $5 fill, not a zero fill. If any supplied figure is positive, or is something you cannot read as a number, the order may have executed and the batch STOPS. Anything else means an order may exist that no cap check accounted for -- an order id in a working state, a confirmed symbol/side/amount that does not match what you asked for (the canonical case is $100 confirmed for a requested $2), a terminal order that simply does not say what it executed, or a response you cannot confidently read at all -- and every one of those STOPS THE BATCH: an order for an amount the remaining orders' caps and buying power were never validated against makes all of that arithmetic wrong, so reconcile it at Gate 8 before placing anything further. An ABSENT fill figure is not a zero -- it establishes nothing about what executed -- but what that means depends on whether you found an order id, and these two cases are OPPOSITE. WITH a usable order id at any level, the broker accepted something and silence about the fill leaves that unresolved, so it HALTS. WITHOUT any usable order id, silence about the fill is the ordinary shape of a refusal -- an untradable ticker reports no fill because there is no order -- so it is ISOLATED and the batch continues, which is the case this entire rule exists to protect, UNLESS the response reports an accepting state (new/queued/confirmed/unconfirmed/partially_filled/filled) per the isolate condition above, which is acceptance evidence even with no id and settles it as a halt. Never read this as 'any missing fill figure halts': that would stop the batch on the first ordinary rejection and undo the change. READ EVERY LEVEL OF THE RESPONSE -- ids, states and fill figures alike -- not only the response -> data -> data.order path: an order can hang off ANY branch, including a sibling of data (`{"success": false, "order": {"id": "ORD", "state": "queued"}, "data": {"error": "timeout"}}`) or an `orders` array, so walk the whole object rather than following one branch. Walk arrays ALL THE WAY DOWN, including one array nested inside another: `{"success": false, "results": [[{"id": "ORD", "state": "queued"}]]}` holds a live order two levels into a list, and skipping it reads as "no order anywhere" -- the isolate verdict, on a response that names a queued order. If you cannot walk some part of it, that is the "could not check" case below, not "nothing there". If the response is so deeply nested or so large that you cannot confidently say you have looked at ALL of it, that is not "no order found" -- it is "could not check", and it STOPS THE BATCH. If ONE level names two DIFFERENT order ids, you cannot tell which one its state and fill figures describe, so that STOPS THE BATCH (the same id repeated under both `id` and `order_id` is one order, not two). And on fill figures specifically: a wrapper can report the executed quantity or dollar amount on the outer envelope beside success, or beside data.order rather than inside it, and a positive or unreadable figure anywhere in the response is spend you cannot account for no matter which level carried it. Only when NO level of the response contradicts the zero may you isolate. THREE further things stop the batch immediately. First, the slot's acceptance window closing mid-batch -- recheck the clock before every placement; placing outside the window is unsafe, not merely unsuccessful. Second, a run of CONSECUTIVE failures reaching config/budgets.json's circuit_breakers.max_consecutive_placement_failures -- read that value from the config file at run time and use whatever it says; this prompt deliberately does not restate the number, so changing the knob changes the behavior: an unbroken run of failures means the broker leg itself is unhealthy (an outage, an expired session, an account block, exhausted buying power), not that one symbol is, and every further placement would be a doomed live call. A successful order resets that streak, so a batch that keeps succeeding between isolated bad symbols runs to completion. Third, a response whose own envelope reports `isError` as the literal boolean true -- the connector/bridge's marker for "this call did not complete", as in `{"isError": true, "error": "timeout"}`. That is the response-shaped twin of a raised call: it tells you the transport failed, NOT whether it failed before the request reached the broker or while carrying the broker's acceptance back, so it STOPS THE BATCH even with no order id and no fill figure anywhere, and an explicit zero does not rescue it. Do not confuse this with an ordinary refusal: a broker declining a ticker reports `success: false` with an error message and carries no `isError` at all, and that still ISOLATES. Fourth, a placement that raises or errors in a way that leaves you unable to establish whether an order landed -- same reasoning as the ambiguous-response rule above: you cannot keep placing against arithmetic you can no longer trust. Report EVERY failed ticker with its own reason in Gate 9 whether or not the batch finished: a completed batch with isolated failures is still a trading failure that must be alerted, and a batch that did stop must name exactly which tickers were never attempted.

GATE 8 - CONFIRM
Wait about 30 seconds, then call get_equity_orders again, following every pagination cursor/page to completion, and report actual submitted and filled orders, not what you intended to place. A just-submitted order sitting beyond the first page must not be reported as absent. Intent logs are how you end up believing in fills that never settled.

GATE 9 - REPORT AND PERSIST EVIDENCE
Write the artifact set FIRST, on EVERY outcome, before any notification: config/market_open_dca.json's state_file_guarantee requires run_state.json, run_summary.json, market_open_signals.csv, and a header-row-even-when-empty submitted_orders.csv under this run's $ROOT (the YYYYMMDD_0935ET directory Gate 5 resolved through dca_paths), plus a refreshed dca_paths.stream_root('market_open_dca', 'latest_market_open_run.json') pointer at that directory. This applies to a clean run, a zero-candidate run, an END_SILENTLY weekend/holiday, and every abort alike -- "a blocked/no-order artifact is valid proof that the 9:35 scheduled task FIRED". Until this was stated here, this gate only notified: it never wrote the set, so a successful run's real orders were invisible to artifact-based reconciliation, drift detection, reporting, and every later slot's prior-allocation scan, and a fire that placed nothing was indistinguishable from a slot that never ran (Codex review: "Persist the required live-run artifacts after placement"). run_state.json follows schemas/run_state.schema.json; a run that exits before Gate 6 ever selects a budget tier writes budget: {"budget_evaluated": false} rather than inventing one. Gate 5's own market_data/candidates files stay alongside it in the same $ROOT. Then, immediately after the artifact write and BEFORE notifying, run the post-artifact drift check this task's own manifest requires (config/scheduled_tasks.json:2ba19526.post_artifact_drift_check, and the repository-wide drift_detection_policy): python scripts/drift_detection.py --run-dir $ROOT --json-out $ROOT/drift_report.json --md-out $ROOT/drift_report.md --slack --fail-on-drift. It reconciles this run's signals against its submitted orders, so an auto-buy signal with no matching order row -- a lost or failed placement -- surfaces as a drift report and an immediate alert instead of silently passing (Codex review: "Run drift detection after persisting market-open artifacts"). Treat a drift failure as an alerting condition on the same three channels, not as a reason to retry or place anything. Only once the artifact set is on disk and the drift check has run, notify:
Clean run: log a compact summary to the in-app message center with order count, total notional, and ticker list. Include the Gate 6.5 line: every ticker resized or zeroed, with its reason code.
Any abort, skip, or cap breach: alert on ALL THREE channels below, in order, and do not stop after the first one succeeds. State the slot, the failing gate, and the reason in each.

Only with evaluated_count > 0 does no_data_count == evaluated_count mean the universe fetch failed. An empty buy list is reachable four other ways, and every one of them is a run that found real candidates and could place none of them: a broken per-ticker fetch (reported, not fatal -- the command still exits 0), a truncated trend fetch turning every price-qualified row into a manual_review_candidate, bars that never reach back to the start of the trend window, and a row whose base and prior-low evidence contradict each other. Each of those looks identical to a quiet tape from buy_count alone. This line previously read "Zero candidates: stay silent" without qualification, which flatly contradicted Gate 5's own alerting rule above and, being the later instruction, could suppress exactly the notification that rule exists to raise (Codex review: "Limit Gate 9 silence to healthy zero-candidate runs"). When any of the four is nonzero, alert per the three channels above naming the specific list. Silence is for an evaluated empty result, never for an unevaluated or withheld one.
