That exemption is for client_id alone and for enclosing levels alone: ref_id, client_order_id and client_order_uuid name the order's idempotency request and nothing else, so an enclosing level carrying a DIFFERENT one of those still STOPS THE BATCH, and all four spellings still apply in full WITHIN the validated order itself and on any separately named order. Compare the client reference EXACTLY, letter for letter -- it is an idempotency key and our own references end in the UPPERCASE ticker, so "...-AAPL" and "...-aapl" are DIFFERENT references and that is a mismatch; ticker and side may be compared ignoring case, because those are the same ticker and the same side however they are spelled. The same applies WITHIN one order: if the order you validated gives two of those reference spellings different values, or names two different tickers, it is contradicting itself about which request it belongs to and confirms nothing -- STOP THE BATCH. And an order id you cannot READ is still an order the broker named: a second order carrying an unreadably large POSITIVE id stops the batch even though your own order confirmed, while 0 or -1 stay the wrapper's way of saying no id was assigned. A repeat that only reports a LATER STATE (queued, then filled) is still one order and is still fine. Read the actual place_equity_order response before you decide, and isolate only when EITHER the response carries no usable order id at ANY nesting level -- check the outer envelope beside success, and data, and data.order, not just the innermost object -- AND says nothing about execution -- no positive or unreadable fill figure, AND reports no state meaning the broker took the order. An id you cannot READ is NOT the same as no id: a number too long to reproduce exactly, or any positive identifier you cannot copy back verbatim, is the broker naming an order you cannot track -- that is AMBIGUOUS and STOPS THE BATCH. Only an absent id, an empty one, or a wrapper's explicit no-id sentinel (0, -1) counts as no id at all. An order id is not the only way a response says an order exists: a response that omits the id but reports new/queued/confirmed/unconfirmed/partially_filled/filled at any level is describing an order the broker accepted, and it STOPS THE BATCH even with no id and no fill figure anywhere. Scope that to those states only. That acceptance rule is NOT limited to responses with no id anywhere: judge it LEVEL BY LEVEL. A level that names no order but reports one of those accepting states stops the batch even when OTHER levels do name orders, and even when every named order is rejected with an explicit zero fill -- `{"state": "queued", "data": {"id": "ORD", "state": "rejected", "cumulative_quantity": 0}}` STOPS THE BATCH. You do not have to decide which reading is right, because both stop it: either that outer level describes a SECOND, unnamed order that is live and in nobody's cap arithmetic, or it describes ORD itself in a state contradicting `rejected`, which is the disagreeing-levels case below. Only the accepting states are read this way. The post-acceptance ones -- `cancelled` and `expired` -- are read here too, but only as a CONTRADICTION test, because those two mean an order existed and was then killed. If NO named order reports the state an unnamed level reports, that level is not restating anything and STOPS THE BATCH: `{"state": "cancelled", "data": {"id": "ORD", "state": "rejected", "cumulative_quantity": 0}}` names only a refused order, so the outer `cancelled` is describing something else, which may have partially filled before it died. If some named order DOES report that same state, it is an ordinary echo and the per-order zero-fill rule below governs it as usual, so a plain cancellation reported at two levels still ISOLATES. An unnamed level that merely RESTATES a named order's own `cancelled` or `expired` is not new information -- the per-order zero-fill rule below already governs those -- and reading it as a second order would stop the batch on every ordinary cancellation. One more thing counts as acceptance evidence when the response names NO order at all: the wrapper's own explicit success flag. If `success`, `ok`, or `approved` is the literal boolean true and you found no order id anywhere, that STOPS THE BATCH even with no state and no fill figure -- the wrapper is telling you the placement went through, and the only reason you are reading this response as a failure is that it omitted the id. It must be a real true, not merely a truthy value: the string "true", the number 1, or any other non-boolean is arbitrary connector data and is NOT this signal, and `success` reported as false is the ordinary refusal this whole rule exists to keep isolating. And like the accepting states, this one applies only where NO order is named -- once a response names an order, a success flag is describing the API call rather than that order's fate, so a named rejected order with an explicit zero still ISOLATES underneath one. WHERE THE RESPONSE NAMES NO ORDER, an absent state, a null state, or a state word you simply do not recognize is the ordinary shape of a refusal (an untradable ticker, a rejected quote, which reports no fill at all) and stays ISOLATED -- treating an unfamiliar state as acceptance would stop the batch on the first ordinary rejection and undo this whole rule. WHERE A NAMED ORDER carries it, the OPPOSITE holds, exactly as the per-order rule below says: the broker named an order, so an absent, null or unreadable state leaves THAT order's status and its spend unresolved and STOPS THE BATCH -- `{"id": "ORD", "state": null}` is a halt, not an isolate. Scope this sentence to the no-id refusal case and nothing wider; read unscoped it contradicts the per-order rule and would let a live named order through. TERMINAL states split in two here, though, and the split matters: `rejected`, `failed` and `voided` mean the broker declined and no order was ever created, so with no id and no fill they ISOLATE; but `cancelled` and `expired` mean an order EXISTED and was then killed -- an order must exist to be cancelled, and must be working to expire -- so it may have partially filled first, and with no id that spend is even less accountable. A missing-id `cancelled` or `expired` therefore STOPS THE BATCH unless every fill figure it supplies is an explicit zero, exactly as it would if it carried an id. A response that omits the id but REPORTS a fill, such as a cancelled state carrying executed_dollar_amount 5, is describing real spend and STOPS THE BATCH. OR EVERY order id it carries -- at EVERY nesting level, because one response can name more than one order: a wrapper's own request identity on the outer envelope and the real broker order inside it -- is in a terminal state (rejected/cancelled/canceled/expired/failed/voided) AND has EVERY fill figure attributable to it be an explicit zero. EVERY ORDER, not merely the first one you find: one live or unreadable order among several terminal ones is still a live order, so if any named order is in a working state, or omits its state everywhere it appears, or has a state you cannot read, the batch STOPS. And an id has to be a REAL identifier before it counts as naming an order at all. A whitespace-only string, a negative or zero number, NaN, infinity, true/false, or a list or object where an id should be are all UNUSABLE -- treat that response as carrying NO order id and judge it by the no-id rules above, including the accepting-state and success-flag checks. An unattributed POSITIVE or unreadable figure is spend you cannot account for and STOPS THE BATCH however many orders are named. An unattributed ZERO is different: it can only vouch for ONE order. EVERY, not any one of them: a quantity and a notional describe the same fill in different units, and a wrapper can populate one while leaving the other at its default, so cumulative_quantity 0 alongside executed_dollar_amount 5 is a real $5 fill, not a zero fill. If any supplied figure is positive, or is something you cannot read as a number, the order may have executed and the batch STOPS. Anything else means an order may exist that no cap check accounted for -- an order id in a working state, a confirmed symbol/side/amount that does not match what you asked for (the canonical case is $100 confirmed for a requested $2), a terminal order that simply does not say what it executed, or a response you cannot confidently read at all -- and every one of those STOPS THE BATCH: an order for an amount the remaining orders' caps and buying power were never validated against makes all of that arithmetic wrong, so reconcile it at Gate 8 before placing anything further. An ABSENT fill figure is not a zero -- it establishes nothing about what executed -- but what that means depends on whether you found an order id, and these two cases are OPPOSITE. WITH a usable order id at any level, the broker accepted something and silence about the fill leaves that unresolved, so it HALTS. If ONE level names two DIFFERENT order ids, you cannot tell which one its state and fill figures describe, so that STOPS THE BATCH (the same id repeated under both `id` and `order_id` is one order, not two). And on fill figures specifically: a wrapper can report the executed quantity or dollar amount on the outer envelope beside success, or beside data.order rather than inside it, and a positive or unreadable figure anywhere in the response is spend you cannot account for no matter which level carried it. Only when NO level of the response contradicts the zero may you isolate. THREE further things stop the batch immediately.
