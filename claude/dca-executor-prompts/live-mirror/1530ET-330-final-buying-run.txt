Compare by MEANING, not by key name: symbol and instrument_symbol are the same field, and ref_id, client_order_id, client_order_uuid and client_id are all the same client reference, so a mismatch spelled differently is still a mismatch. ONE EXCEPTION, and only one: a client_id on an ENCLOSING level -- a wrapper around the order you validated -- is where a transport or connector puts its OWN request id, so a wrapper client_id that differs from the order's own reference is ordinary metadata and does NOT stop the batch. That exemption is for client_id alone and for enclosing levels alone: ref_id, client_order_id and client_order_uuid name the order's idempotency request and nothing else, so an enclosing level carrying a DIFFERENT one of those still STOPS THE BATCH, and all four spellings still apply in full WITHIN the validated order itself and on any separately named order. Compare the client reference EXACTLY, letter for letter -- it is an idempotency key and our own references end in the UPPERCASE ticker, so "...-AAPL" and "...-aapl" are DIFFERENT references and that is a mismatch; ticker and side may be compared ignoring case, because those are the same ticker and the same side however they are spelled. The same applies WITHIN one order: if the order you validated gives two of those reference spellings different values, or names two different tickers, it is contradicting itself about which request it belongs to and confirms nothing -- STOP THE BATCH. And an order id you cannot READ is still an order the broker named: a second order carrying an unreadably large POSITIVE id stops the batch even though your own order confirmed, while 0 or -1 stay the wrapper's way of saying no id was assigned. A repeat that only reports a LATER STATE (queued, then filled) is still one order and is still fine. Read the actual place_equity_order response before you decide, and isolate only when EITHER the response carries no usable order id at ANY nesting level -- check the outer envelope beside success, and data, and data.order, not just the innermost object -- AND says nothing about execution -- no positive or unreadable fill figure, AND reports no state meaning the broker took the order. An id you cannot READ is NOT the same as no id: a number too long to reproduce exactly, or any positive identifier you cannot copy back verbatim, is the broker naming an order you cannot track -- that is AMBIGUOUS and STOPS THE BATCH. Only an absent id, an empty one, or a wrapper's explicit no-id sentinel (0, -1) counts as no id at all. An order id is not the only way a response says an order exists: a response that omits the id but reports new/queued/confirmed/unconfirmed/partially_filled/filled at any level is describing an order the broker accepted, and it STOPS THE BATCH even with no id and no fill figure anywhere. Scope that to those states only. That acceptance rule is NOT limited to responses with no id anywhere: judge it LEVEL BY LEVEL. A level that names no order but reports one of those accepting states stops the batch even when OTHER levels do name orders, and even when every named order is rejected with an explicit zero fill -- `{"state": "queued", "data": {"id": "ORD", "state": "rejected", "cumulative_quantity": 0}}` STOPS THE BATCH. You do not have to decide which reading is right, because both stop it: either that outer level describes a SECOND, unnamed order that is live and in nobody's cap arithmetic, or it describes ORD itself in a state contradicting `rejected`, which is the disagreeing-levels case below. Only the accepting states are read this way. The post-acceptance ones -- `cancelled` and `expired` -- are read here too, but only as a CONTRADICTION test, because those two mean an order existed and was then killed. If NO named order reports the state an unnamed level reports, that level is not restating anything and STOPS THE BATCH: `{"state": "cancelled", "data": {"id": "ORD", "state": "rejected", "cumulative_quantity": 0}}` names only a refused order, so the outer `cancelled` is describing something else, which may have partially filled before it died. If some named order DOES report that same state, it is an ordinary echo and the per-order zero-fill rule below governs it as usual, so a plain cancellation reported at two levels still ISOLATES. An unnamed level that merely RESTATES a named order's own `cancelled` or `expired` is not new information -- the per-order zero-fill rule below already governs those -- and reading it as a second order would stop the batch on every ordinary cancellation. One more thing counts as acceptance evidence when the response names NO order at all: the wrapper's own explicit success flag. If `success`, `ok`, or `approved` is the literal boolean true and you found no order id anywhere, that STOPS THE BATCH even with no state and no fill figure -- the wrapper is telling you the placement went through, and the only reason you are reading this response as a failure is that it omitted the id. It must be a real true, not merely a truthy value: the string "true", the number 1, or any other non-boolean is arbitrary connector data and is NOT this signal, and `success` reported as false is the ordinary refusal this whole rule exists to keep isolating. And like the accepting states, this one applies only where NO order is named -- once a response names an order, a success flag is describing the API call rather than that order's fate, so a named rejected order with an explicit zero still ISOLATES underneath one. WHERE THE RESPONSE NAMES NO ORDER, an absent state, a null state, or a state word you simply do not recognize is the ordinary shape of a refusal (an untradable ticker, a rejected quote, which reports no fill at all) and stays ISOLATED -- treating an unfamiliar state as acceptance would stop the batch on the first ordinary rejection and undo this whole rule. WHERE A NAMED ORDER carries it, the OPPOSITE holds, exactly as the per-order rule below says: the broker named an order, so an absent, null or unreadable state leaves THAT order's status and its spend unresolved and STOPS THE BATCH -- `{"id": "ORD", "state": null}` is a halt, not an isolate. Scope this sentence to the no-id refusal case and nothing wider; read unscoped it contradicts the per-order rule and would let a live named order through. TERMINAL states split in two here, though, and the split matters: `rejected`, `failed` and `voided` mean the broker declined and no order was ever created, so with no id and no fill they ISOLATE; but `cancelled` and `expired` mean an order EXISTED and was then killed -- an order must exist to be cancelled, and must be working to expire -- so it may have partially filled first, and with no id that spend is even less accountable. A missing-id `cancelled` or `expired` therefore STOPS THE BATCH unless every fill figure it supplies is an explicit zero, exactly as it would if it carried an id. A response that omits the id but REPORTS a fill, such as a cancelled state carrying executed_dollar_amount 5, is describing real spend and STOPS THE BATCH. OR EVERY order id it carries -- at EVERY nesting level, because one response can name more than one order: a wrapper's own request identity on the outer envelope and the real broker order inside it -- is in a terminal state (rejected/cancelled/canceled/expired/failed/voided) AND has EVERY fill figure attributable to it be an explicit zero. EVERY ORDER, not merely the first one you find: one live or unreadable order among several terminal ones is still a live order, so if any named order is in a working state, or omits its state everywhere it appears, or has a state you cannot read, the batch STOPS. Count DISTINCT orders, though, not envelope levels: a wrapper often echoes the SAME id at two levels, and that is one order described twice, not two orders. Group the levels by order id first, then judge each order from all of its own levels together -- so `{"id": "ORD", "state": "rejected", "cumulative_quantity": 0, "data": {"id": "ORD", "state": "rejected"}}` is one ordinary rejected order with an explicit zero fill and is ISOLATED, even though the inner level carries no fill figure of its own. Two levels of one order that DISAGREE -- rejected outside, queued inside -- still stop the batch. Match ids exactly -- same characters AND same type. And an id has to be a REAL identifier before it counts as naming an order at all. A whitespace-only string, a negative or zero number, NaN, infinity, true/false, or a list or object where an id should be are all UNUSABLE -- treat that response as carrying NO order id and judge it by the no-id rules above, including the accepting-state and success-flag checks. This matters because naming an order is what routes a response PAST those checks: `{"success": true, "id": "   ", "state": "rejected", "cumulative_quantity": 0}` has an explicit success flag and no real identifier anywhere, so it STOPS THE BATCH rather than reading as one tidy rejected order. A genuinely valid id under a success flag is unchanged and still ISOLATES. Do not treat ids differing only in letter case as the same order, and do not treat the number 1 and the string "1" as the same order either. Merging is the dangerous direction, because it lets one order's zero fill vouch for another order that reported nothing; splitting one order into two at worst costs you a halt. And ask the zero-fill question ONCE PER ORDER, not once for the response as a whole: one order's explicit zero must never answer for a sibling that said nothing about its own fill. Attribute the figures by where they sit -- a fill figure on an envelope that NAMES an order describes THAT order, and a fill figure on an envelope naming no order is unattributed. An unattributed POSITIVE or unreadable figure is spend you cannot account for and STOPS THE BATCH however many orders are named. An unattributed ZERO is different: it can only vouch for ONE order. If the response names exactly one order, that zero plainly describes it and the response is proof. If it names two or more, one zero cannot say which of them it describes -- or whether it is their sum -- so it proves NONE of them, and each order needs its own explicit zero or the batch STOPS. So `{"id": "REQ", "state": "rejected", "cumulative_quantity": 0, "data": {"order": {"id": "ORD", "state": "cancelled"}}}` STOPS THE BATCH -- REQ's zero says nothing about ORD, which is a real accepted order that is silent about what it executed -- while the same response with `"cumulative_quantity": 0` inside ORD too is proof and isolates. EVERY, not any one of them: a quantity and a notional describe the same fill in different units, and a wrapper can populate one while leaving the other at its default, so cumulative_quantity 0 alongside executed_dollar_amount 5 is a real $5 fill, not a zero fill. If any supplied figure is positive, or is something you cannot read as a number, the order may have executed and the batch STOPS. Anything else means an order may exist that no cap check accounted for -- an order id in a working state, a confirmed symbol/side/amount that does not match what you asked for (the canonical case is $100 confirmed for a requested $2), a terminal order that simply does not say what it executed, or a response you cannot confidently read at all -- and every one of those STOPS THE BATCH: an order for an amount the remaining orders' caps and buying power were never validated against makes all of that arithmetic wrong, so reconcile it at Gate 8 before placing anything further. An ABSENT fill figure is not a zero -- it establishes nothing about what executed -- but what that means depends on whether you found an order id, and these two cases are OPPOSITE. WITH a usable order id at any level, the broker accepted something and silence about the fill leaves that unresolved, so it HALTS. WITHOUT any usable order id, silence about the fill is the ordinary shape of a refusal -- an untradable ticker reports no fill because there is no order -- so it is ISOLATED and the batch continues, which is the case this entire rule exists to protect, UNLESS the response reports an accepting state (new/queued/confirmed/unconfirmed/partially_filled/filled) per the isolate condition above, which is acceptance evidence even with no id and settles it as a halt. Never read this as 'any missing fill figure halts': that would stop the batch on the first ordinary rejection and undo the change. READ EVERY LEVEL OF THE RESPONSE -- ids, states and fill figures alike -- not only the response -> data -> data.order path: an order can hang off ANY branch, including a sibling of data (`{"success": false, "order": {"id": "ORD", "state": "queued"}, "data": {"error": "timeout"}}`) or an `orders` array, so walk the whole object rather than following one branch. Walk arrays ALL THE WAY DOWN, including one array nested inside another: `{"success": false, "results": [[{"id": "ORD", "state": "queued"}]]}` holds a live order two levels into a list, and skipping it reads as "no order anywhere" -- the isolate verdict, on a response that names a queued order. If you cannot walk some part of it, that is the "could not check" case below, not "nothing there". If the response is so deeply nested or so large that you cannot confidently say you have looked at ALL of it, that is not "no order found" -- it is "could not check", and it STOPS THE BATCH. If ONE level names two DIFFERENT order ids, you cannot tell which one its state and fill figures describe, so that STOPS THE BATCH (the same id repeated under both `id` and `order_id` is one order, not two). And on fill figures specifically: a wrapper can report the executed quantity or dollar amount on the outer envelope beside success, or beside data.order rather than inside it, and a positive or unreadable figure anywhere in the response is spend you cannot account for no matter which level carried it. Only when NO level of the response contradicts the zero may you isolate. THREE further things stop the batch immediately. First, the slot's acceptance window closing mid-batch -- recheck the clock before every placement; placing outside the window is unsafe, not merely unsuccessful. Second, a run of CONSECUTIVE failures reaching config/budgets.json's circuit_breakers.max_consecutive_placement_failures -- read that value from the config file at run time and use whatever it says; this prompt deliberately does not restate the number, so changing the knob changes the behavior: an unbroken run of failures means the broker leg itself is unhealthy (an outage, an expired session, an account block, exhausted buying power), not that one symbol is, and every further placement would be a doomed live call. A successful order resets that streak, so a batch that keeps succeeding between isolated bad symbols runs to completion. Third, a response whose own envelope reports `isError` as the literal boolean true -- the connector/bridge's marker for "this call did not complete", as in `{"isError": true, "error": "timeout"}`. That is the response-shaped twin of a raised call: it tells you the transport failed, NOT whether it failed before the request reached the broker or while carrying the broker's acceptance back, so it STOPS THE BATCH even with no order id and no fill figure anywhere, and an explicit zero does not rescue it. Do not confuse this with an ordinary refusal: a broker declining a ticker reports `success: false` with an error message and carries no `isError` at all, and that still ISOLATES. Fourth, a placement that raises or errors in a way that leaves you unable to establish whether an order landed -- same reasoning as the ambiguous-response rule above: you cannot keep placing against arithmetic you can no longer trust. Report EVERY failed ticker with its own reason in Gate 9 whether or not the batch finished: a completed batch with isolated failures is still a trading failure that must be alerted, and a batch that did stop must name exactly which tickers were never attempted.

GATE 8 - CONFIRM
Wait about 30 seconds, then call get_equity_orders again, following every pagination cursor/page to completion, and report actual submitted and filled orders, not what you intended to place. A just-submitted order sitting beyond the first page must not be reported as absent. Intent logs are how you end up believing in fills that never settled.

GATE 9 - REPORT
Clean run: log a compact summary to the in-app message center with order count, total notional, and ticker list. Include the Gate 6.5 line: every ticker resized or zeroed, with its reason code.
Any abort, skip, or cap breach: alert on ALL THREE channels below, in order, and do not stop after the first one succeeds. State the slot, the failing gate, and the reason in each.
1. IN-APP MESSAGE CENTER, primary (config/notifications.json alert routing).
2. REPO ALERT FILE, durable fallback. If the repo is reachable, write the same text to ${DCA_CRON_TRACKING_ROOT:-/home/user/workspace/cron_tracking}/ce16ba6b/scheduled_runs/alerts/<YYYY-MM-DD>-<slot>-<gate>.txt (dca_paths.stream_root('ce16ba6b', 'scheduled_runs', 'alerts', ...) -- never a bare repo-relative artifacts/ directory, which .gitignore discards: 23 of the 2026-08 alerts claimed a durable copy under artifacts/alerts/ and every one of them was lost) so the alert survives the session. 3. EMAIL, belt-and-braces. SEND the same text to the operator email configured for alerts (never hardcode a personal address), with a subject naming the slot, the ET date, and the failing gate so the alert is greppable later. Send it -- do not leave it sitting as a draft. An earlier revision of this line asserted the email connector had no send capability and told you to create a draft instead; that produced ~50 undelivered alert drafts between 2026-08-06 and 2026-08-26, none of which the operator read (see docs/alert_digest.md). Channels 1 and 2 were written before this step and cannot mention a failure that had not happened yet, so go back to them: post a follow-up note to the message center and, if the repo is reachable, append the same line to the channel-2 alert file, naming the slot, the gate, and why the send failed. A draft is NOT delivery and must never be the only channel used.
Zero candidates: stay silent ONLY when the Gate 5 document shows a genuinely quiet, fully evaluated tape -- provider_error_count: 0 AND manual_review_count: 0. An empty buy list is reachable two other ways, and both are runs that found real candidates and could place none of them: a broken per-ticker fetch (reported, not fatal -- the command still exits 0), and a truncated trend fetch turning every price-qualified row into a manual_review_candidate. Either looks identical to a quiet tape from buy_count alone. When either count is nonzero, alert per the three channels above naming it. Silence is for an evaluated empty result, never for an unevaluated one. STANDING PROHIBITIONS
Never place a sell. Never touch options, crypto, or margin. Never retry a failed submit. Never build a buy list without the repo. Never place an order larger than Gate 6.5's buy_usd for that ticker. Never override a gate because the situation looks like an exception. If you find yourself reasoning toward "the safe thing here is to place the order anyway," that is the signal to stop and alert instead.
