# Self-Heal Coding Agent Setup

This repository is equipped with an adaptive self-healing workflow, designed to detect and repair codebase drift (linting, formatting, missing types, snapshot drift). It operates automatically and submits PRs for human review.

## Architecture

The self-heal system is composed of several components:

1. **`scripts/healthcheck.py`**: A deterministic gate script that verifies codebase health. It mirrors ci.yml's checks: `ruff check` for linting, type checking with `pyright`, `pytest` (coverage-gated) for tests, the dry-run demo smoke test, and `pip-audit`. It does not run `ruff format --check` -- there is no formatting gate. It exits with code 0 if healthy, 1 if not.
2. **`scripts/self_heal.py`**: The repair pipeline. It executes a sequence of idempotent steps (dependency installation, linting auto-fixes, etc.) and re-evaluates health after each step.
3. **`scripts/compute_schedule.py`**: Telemetry engine. It analyzes commit frequency to compute a suggested cron cadence and writes it both to `.github/self-heal-schedule.yml` and to the `# AUTO-UPDATED` cron line in `.github/workflows/self-heal.yml` (see Triggers below).
4. **`.github/workflows/self-heal.yml`**: The primary GitHub Actions workflow. It triggers on its own telemetry-computed schedule and reactively on CI failure (see Triggers below). It runs the repair and automatically creates a PR if a fix is found.
5. **`.github/workflows/compute-schedule.yml`**: A secondary workflow that periodically runs the telemetry engine to update the schedule.
6. **`.github/self-heal-schedule.yml`**: The metadata file holding the current schedule and the rationale behind it.

## Triggers

`.github/workflows/self-heal.yml` (the repair workflow) triggers two ways:

* **Manual Dispatch (`workflow_dispatch`):** Allows an operator to manually trigger a self-heal run.
* **Scheduled:** Runs on the cron cadence recorded in the `# AUTO-UPDATED` line under its `schedule:` trigger, which `compute-schedule.yml` keeps in sync with the telemetry-computed (or manually overridden) value in `.github/self-heal-schedule.yml`.
* **Reactive (CI failure):** Runs when the `CI` workflow (`ci.yml`) completes with a failure on `main`. It only proceeds past the "Check reactive trigger scope" step when the failing job is one `scripts/healthcheck.py` can actually validate (the core lint/test/audit job) -- a failure isolated to an independent sibling suite (production-safe-agent-loop, ticker-advisor, ml-forecaster, wondrous-octopus) is skipped, since the repair pipeline has no way to install or fix those.

It deliberately has no `workflow_dispatch` trigger -- see that file's own header comment for the trust-boundary reasoning (a `workflow_dispatch` run would execute an arbitrary ref's own copy of this file with a `contents: write`/`pull-requests: write` token).

`.github/workflows/compute-schedule.yml` (the separate schedule-telemetry updater) also triggers only one way, for the same trust-boundary reason (see its own header comment):

* **Scheduled:** Runs monthly to recompute a suggested cadence from repository activity and write it to `.github/self-heal-schedule.yml`. It deliberately has no `workflow_dispatch` either -- it holds `contents`/`pull-requests`/`issues` write permissions, and a dispatch-selected ref's own copy of the workflow file could remove any ref-restricting check inside it.

## Reviewer Checklist

When reviewing a PR generated by the self-heal workflow, consider the following:

* **Diff content:** Ensure the changes actually resolve the drift (e.g., formatter updates, missing type imports) without altering business logic.
* **Secrets:** No automated secret scan runs before a self-heal PR is opened -- manually verify that no sensitive data (API keys, passwords, credentials, account identifiers) was introduced.
* **Test coverage:** Ensure any new files or modifications don't break the existing test coverage negatively.

## Known Recurring Failures

Failures that are outside `scripts/self_heal.py`'s repair steps but have hit agent PRs more
than once, with the fix that ended them. Check here before treating one as new drift.

### Merge conflicts on `pr_description.md` (fixed 2026-10-29, PR #2047)

* **Symptom:** an open agent PR (most often from Jules) shows "This branch has conflicts that
  must be resolved", and the only non-code file listed is `pr_description.md`. PR #2033 hit this
  twice in one day. #1926 had to remove a stray `pr_description.txt` for the same reason.
* **Cause:** agents wrote their PR text into a tracked `pr_description.md` at the repo root.
  Every merge overwrote the one shared copy with that PR's description, so every other open
  agent PR conflicted with `main` on it. Nothing in the repo reads the file.
* **Fix in place:** the file is untracked and `/pr_description.*` is in `.gitignore`.
  `AGENTS.md` ("Pull request expectations") tells agents to put the description in the PR
  body instead.
* **If it comes back** (an agent force-adds the file, or an older branch still carries it):
  resolve by deleting the file from that PR, not by picking either side's text:

  ```bash
  git fetch origin && git merge origin/main
  git rm pr_description.md        # or pr_description.txt
  git commit --no-edit && git push
  ```

  The PR's description already lives in the PR body, so nothing is lost. The self-heal
  workflow does not run this for you: it repairs `main`'s CI health and pushes only to its own
  `selfheal-repair-` branches, never to another PR's branch.

## Overriding the Schedule

If you want to manually set the scheduled cadence and have it stick, bypassing the telemetry engine entirely:

1. Edit `.github/self-heal-schedule.yml`.
2. Update the `schedule:` and `rationale:` values, and set `override: true`.
3. Commit and push the changes.
4. With `override: true` set, `compute_schedule.py` skips the telemetry recompute on every subsequent run and only re-syncs `self-heal.yml`'s cron to your override value -- so the value you chose is never silently replaced by the next scheduled run of `compute-schedule.yml`. Set `override: false` (or remove the line) to hand control back to the telemetry engine.

Without an override, `compute-schedule.yml` recomputes the cadence monthly from `git log` commit counts over the trailing 30 days (see `scripts/compute_schedule.py`'s `compute_cadence()`).
