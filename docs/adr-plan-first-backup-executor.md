# Plan-first backup executor

Status: proposed (2026-10-06); D4 amended 2026-10-22 (Normal-only, trim to fit). Phase 1 of a six-phase change; no code is implemented by this
document. Operator approval is required before Phase 2 (tests).

## Context

Claude on the Mac Studio is the primary executor for seven slots (09:35, 10:30, 11:30, 12:30,
13:30, 14:30, 15:30 ET). Perplexity scheduled tasks are delayed backups (09:55, 10:50, 11:50,
12:50, 13:50 and 14:50, 15:45 ET; see `config/scheduled_tasks.json`
`standing_perplexity_backup_policy`). Broker order history is the only evidence of what was
bought.

Today the backup prompts make the LLM do the sizing math in prose. The repo already holds the
tested logic for it, so the prose is a second, unverified implementation that drifts:

- Gate 5 candidates: `scripts/stream_candidates.py` (the `cands` and `planner_candidates` rows),
  using `near_close_dca.raw_ladder_multiplier` and the $1 or $2 base selection.
- Caps, whitelist, priority, one order per ticker: `dca_runner.plan_orders`.
- Idempotency key: `dca-runner-<slot_id>-<trading_day>-<TICKER>` (`docs/live_wiring.md`).

Findings from Phase 0 that shape this decision:

- The repo already designs per-ticker exclusion, so a partly finished Claude batch can be
  completed (`claude/PERPLEXITY-CLAUDE-COORDINATION.md` section 1). The
  `standing_perplexity_backup_policy.mechanism` text still says to stand down on any Claude
  evidence, which contradicts it. The live backup prompts are not in this repo.
- The effective per-order ceiling is $16 (`dca_runner.MAX_PER_ORDER_USD`, derived from the
  ladder; `config/budgets.json` `circuit_breakers.max_per_order_usd`). "$10" survives only in
  stale prose.
- RVI, VCX and TRLV are active in `config/tickers.json` (re-added 2026-08-16). QBUT is the only
  excluded symbol.

## Decision

Introduce a plan file and move backup sizing into code.

1. **Plan file** (`schemas/order_plan.schema.json`, draft below). The primary slot runner writes
   it before placing orders. It lists the slot's intended buys in allocation-priority order.
2. **Mac-first backup.** Each backup run, after its unchanged gates and double evidence poll,
   checks for the Mac Studio with a bounded call (D8: 60 seconds). If reachable and a valid plan
   for this day and slot exists, the backup places only planned orders that the broker history
   shows unplaced. This replaces the 2026-09-23 "never check the Mac" rule.
3. **Mac compute.** Reachable but no valid plan: run the repo planner on the Mac through
   `run_local_subagent`, so real repo code runs and nothing is vendored.
4. **Cloud compute.** Mac offline, not found, timed out, or device call error: run a stdlib-only
   single-file build of the planner (`dist/backup_planner.py`, generated by a script from repo
   code, stamped with source commit and content hash, with a drift test) in the Perplexity
   sandbox on data the agent fetched from Robinhood and dumped to files.
5. **Fail closed.** Planner error or missing inputs: no orders, status `failed_unexpected_error`,
   notify. Any validation failure of a plan file yields an empty plan and a structured error,
   never an exception to the caller and never a partial buy.
6. **Evidence.** The state record carries `plan_source` of `mac_plan`, `mac_compute` or
   `cloud_compute`. Mac files, logs and plans are inputs only, never purchase evidence.
7. **Code re-validates on every path:** universe, do-not-buy list (QBUT), per-order cap, daily and
   weekly caps against a fresh full-day order pull, no duplicate same-day ticker, and a fresh
   quote still below the prior close.

### Plan file schema (draft)

The authoritative draft is `schemas/order_plan.schema.json`. Shape:

```json
{
  "schema_version": 1,
  "trading_day": "2026-10-06",
  "slot": "1130",
  "generated_at_et": "2026-10-06T11:30:12-04:00",
  "generator": "claude",
  "ladder_version": "2026-10-04",
  "universe_hash": "<sha256 of sorted active tickers joined by newline, plus trailing newline>",
  "orders": [
    {
      "symbol": "MU",
      "notional_usd": 6.0,
      "multiplier": 3.0,
      "drop_pct": 2.4,
      "decision_price": 100.0,
      "prior_close": 102.46,
      "prior_low": 100.5,
      "ref_id": "dca-runner-1130-2026-10-06-MU"
    }
  ]
}
```

Serialization is canonical (sorted keys, fixed separators, trailing newline, orders in
allocation-priority order) so identical inputs give byte-identical files.

Mapping to existing fields (`scripts/stream_candidates.py:1363`): `notional_usd` from
`desired_usd`, `decision_price` from `current_price`, `prior_low` and `prior_close` unchanged.

### Amendments from implementation (Phases 2 to 4)

- **Sizing source.** Live sizing uses `config/per_ticker_sizing.json` (interpolated, $1 base) for every
  active ticker; `config/sizing_ladder.json` is only the fallback. `ladder_version` is therefore the
  composite `<sizing_ladder version>+<per_ticker_sizing version>` (`dca_order_plan.current_ladder_version`),
  and `drop_pct` may be below 0.1.
- **Slot ids** are `0935`..`1530` with no `ET` suffix, matching `dca_runner.SLOTS` and `ref_id`.
- **Caps are written out** in `dca_order_plan._cap_errors` (all-or-nothing, the default) and
  `dca_order_plan._fit_prefix` (trim to fit, which the backup planner opts into, see D4) instead of calling
  `plan_orders`, whose multiplier-consistency check is bound to the calibration files read at import time.
  `execute_plan` still runs `plan_orders` at placement.
- **Primary-side emit** is `scripts/emit_order_plan.py`, run as the first step of Gate 7 in each live-mirror
  prompt, because placement in the live prompts is prose and not a code runner. A failed emit writes nothing,
  exits 2, and does NOT block the primary's own placement (only the backup depends on the plan). Live
  scheduled bodies are unchanged until a human repastes the mirrors.
- **Cloud single-file build (2026-10-08): a zipapp, not a condensed script.** `scripts/build_backup_planner.py`
  packs the planner's static import closure (about 27 repo modules, 1.4 MB zipped) plus the nine config files it
  opens into `backup_planner.pyz`, run as `python3 backup_planner.pyz <plan|compute|finalize|assemble-market-data> ...`.
  A hand-trimmed single script would be a second copy of the sizing, cap and order-history logic. The build is
  deterministic and stamped (`--build-info`: source commit, content hash); `--check` reports drift. A bootstrap
  extracts the config to a temp directory, overrides any host `DCA_CONFIG_DIR`, and fails closed with one JSON
  document on a too-old Python. The `dca_ladder_core` extraction (PR 1624) was the first step but the shipped
  file runs the real modules. The built file is not committed (`dist/` is gitignored); how it reaches the
  Perplexity sandbox is still undecided.
- **Safety gate (2026-10-08), all seven slots.** `compute --market-data FILE --deployed-last-7d-usd N` runs the
  slot's Gate 5 (`scripts.generate_buy_candidates.generate_candidates` for 15:30,
  `scripts.stream_candidates` for the other six) and plans exactly the placeable BUYs it
  reaches, with its sizing, kill switch and provider-error handling, then applies the same Normal-tier caps (trimmed to fit, D4) as
  the quotes path (`dca_order_plan.plan_from_decisions`). `scripts/assemble_market_data.py` turns the raw
  Robinhood responses the Perplexity task dumps into that payload using the repo's `RobinhoodDataProvider`
  parsing, so the task reshapes nothing. Stream computation uses the default decision anchor and excludes
  planner-incompatible candidates. The backup's morning spec disables the retired preflight; its midday spec
  uses Robinhood with the default cadence and no per-ticker source exception. Primary specs and the three live
  execution entry points remain unchanged. `finalize` returns `SHADOW_ONLY` for a computed plan unless it is
  given `--local-status off|errored|unreachable` (switch turned on 2026-10-13, see the operator decision below).
- **The 7-day deployment figure (implemented 2026-10-08).** The primary derives it from run-state artifacts on the
  Mac, which the cloud cannot read. The cloud path derives it from broker order history instead:
  `compute --deployed-last-7d-usd auto` calls `dca_order_plan.trailing_deployed_usd`, the trailing-7-day total of
  ALL agents' committed buys. That is at least the afternoon-only figure, so an error can only trip the kill
  switch (1x cap) earlier, never later; a malformed amount fails closed instead of reading as zero. The generated
  prompts fetch seven days of order history (covering both the ISO-week cap and this figure) and never sum
  anything by hand.
- **Prompts regenerated (2026-10-08).** They run the stamped `backup_planner.pyz`, verify it with `--build-info`,
  and take the safety-gate path for all seven slots in `backup_planner.GATED_SLOTS`. The `universe` command
  supplies buyable symbols from config; prompts contain no stock list. Computed plans still report `shadow_only`.

## Alternatives considered

| Option | Why not |
| --- | --- |
| Keep prose-only prompts | Sizing and cap math stay untested and drift from the repo, which is the problem being solved. |
| New standalone planner | A second implementation of ladder and caps. `plan_orders` and Gate 5 already exist (CLAUDE.md warns duplicated logic drifts silently). |
| Change `gate_sole_executor`'s return shape (SEVEN-SLOT-TRANSITION-PROPOSAL section 3) | Shared, load-bearing, and out of scope. Reconciliation is a new pure function; existing callers are untouched. |
| Repo-derived planner (chosen) | Reuses the tested logic; the only new code is plan I/O, validation and reconciliation. |

## Consequences

- Backup sizing is tested code. The backup depends on the Mac being reachable for the best path
  and degrades to compute paths otherwise.
- `dist/backup_planner.py` is a generated artifact that must be kept in sync; a test fails on
  drift.
- The primary runner gains a write step before placement (Phase 4), a behavior change to a live
  path that needs its own review and acceptance run.
- Plan files never become evidence. Reporting and run classification are unchanged.
- New top-level modules are added to `pyproject.toml` `py-modules` per the repo invariant. The schema file
  is documentation that no code reads at runtime, and the repo ships no other schema in `data-files`, so it
  is deliberately not packaged (corrected after review; an earlier draft of this ADR said otherwise).

### Design gaps found in review (2026-10-07)

Raised by an automated review of PR #1619 and verified against the code and config. None affects the
primary Claude slots. Status after the follow-up change:

1. **Cross-slot top-ups: fixed.** `config/budgets.json` `one_order_per_ticker_per_day` is false, so a later
   slot may buy a ticker again, resized by `scripts/same_day_top_up_gate.py`. A Claude plan already carries
   the resized notional, so `finalize` reconciles it against THIS slot's window only
   (`dca_order_plan.placement_window`, `reconcile(scope="slot")`); a computed plan cannot resize, so it keeps
   the day-wide exclusion. The prompts' rule 5 now reads "one order per ticker per slot".
2. **Compute path is not the Gate 5 signal path: fixed for all seven slots (2026-10-08).** `compute --market-data`
   reuses the slot's candidate generator, including trend and data-confidence gates. The legacy `--quotes`
   path remains ladder-only. Operator decision 2026-10-13: `COMPUTE_PLACEMENT_ENABLED` is on, so a backup that
   cannot reach the Mac places its own computed plan. `finalize` places only when told `--local-status off`,
   `errored` or `unreachable`; absent, `unknown`, `in_progress` and `succeeded` stay `SHADOW_ONLY`. The shadow run
   is no longer a precondition. With no Mac the heartbeat `claim` is skipped and the broker order history (two polls,
   per-order repull, caps, spread check) is the only duplicate protection, as in the pre-2026-10-06 design.
3. **Buying power: fixed.** `compute` and `finalize` require `--buying-power` and fail closed when it is
   missing, unusable, or below the batch total.
4. **Spread (Gate 6.7): fixed.** `finalize` requires `--fresh-spreads`; a missing, crossed, unusable, or wide
   spread skips that ticker only, using `near_close_dca._quote_bid_ask` validity and
   `StrategyConfig.max_bid_ask_spread_pct`.

### Known limitations

- **15:45 ET backup may run out of time before 16:00 ET** because of the Mac-first check. Accepted
  by the operator on 2026-10-06. No slot-specific timeout or optimization is added.
- D6 is open; idempotency on `ref_id` is not relied on.
- Two engines can still start simultaneously and both see an empty window (accepted risk,
  coordination doc section 1).
- Perplexity cannot read this repo, so the Phase 5 prompts remain a manual paste step.

## Amendment: execution routing (2026-10-08)

Status: implemented as `dca_execution_router.py` (pure decision and log layer; no ordering, no credentials,
no ladder or sizing-suggester wiring). Wraps `dca_order_plan.choose_plan_path`; adds no second path selector.

- **Roles.** `LOCAL` is the sole buyer when alive. `CLOUD` is calculation-only: `guard_broker` raises
  `OrderPlacementForbidden` on `place_order`. `PERPLEXITY` acts only when local is `UNREACHABLE`, `OFF` or `ERRORED`.
- **Detection (operator-approved).** A bounded probe (`DCA_LOCAL_PROBE_TIMEOUT_S`, default 60) maps
  `choose_plan_path` statuses: offline/not_found -> OFF, timeout -> UNREACHABLE, device_error -> ERRORED, anything
  else -> UNKNOWN. With the Mac online, the slot lease is the heartbeat: success marker -> SUCCEEDED, failure marker
  -> ERRORED, no lease -> OFF (act), lease younger than `DCA_LOCAL_HEARTBEAT_STALE_S` (default 300) -> IN_PROGRESS,
  older -> ERRORED. Lease not read -> UNKNOWN.
- **UNKNOWN stands down** and alerts, since a false fallback risks a duplicate buy. Broker order history remains the
  only purchase evidence; the routing log (`<cron root>/execution_routing/routing_<day>.jsonl`: path, reason,
  timestamp) is only a second guard, and a recorded buy for the slot blocks any later fallback.
- **Wiring.** `scripts/local_heartbeat.py` (`start`/`beat`/`finish` for the local run, `status` for the backup; `start` mints
  a per-run token so a duplicate start is refused and only the owning run can beat or finish) and the
  regenerated Perplexity prompts (step 3 "LOCAL FIRST") implement the table above.
- **Not yet done.** The local live-mirror prompts must call `start` (keep the `token` it prints), `beat --token` (at least every 60s) and
  `finish --token`, and a
  human must repaste the regenerated Perplexity prompts. Until the local side writes the lease, an online Mac reads
  as `off` and the backup would act.

## Rollback

Every phase is additive. The backup prompts switch back by repasting the previous prompt text
(kept under `claude/dca-executor-prompts/`); the primary emit step (Phase 4) is removed by
reverting its commit, and the plan file is ignored by anything that does not opt in. No existing
`gate_sole_executor` or `plan_orders` caller changes behavior. Shadow mode (Phase 6) runs at
least five trading days with no placement before any live decision.

### Stage 1: every stream slot alike (2026-10-09)

Owner direction (2026-10-08): nothing is special about 10:30 or 12:30; they differ only in time. No slot may depend
on the retired 09:45 pre-flight, the Finance connector, Yahoo, or a per-ticker source exception, and no prompt may
name a stock.

- **All seven slots are gated** (`backup_planner.GATED_SLOTS`). The six executor-class slots run the primary's own
  stream CLI path (`stream_candidates._run_with_args`) on the Robinhood payload and plan its `cands` BUY rows, minus
  `planner_incompatible_tickers`. `scripts/backup_stream_specs.py` returns each slot's own primary spec as-is. Stage 2 made
  10:30 and 12:30 plain Robinhood-sourced specs (the 09:45 pre-flight was retired, and 12:30 became Robinhood-primary
  with default bars and no `ticker_source_overrides`, as 09:35 did on 2026-09-09), so the backup carries no
  adaptation of its own and cannot size differently from the primary.
- **15:30 is filtered by `planner_incompatible`, with the calibration bounds in the row.** A bare 4-field row is judged
  against the global ladder and flags nearly every calibrated ticker (the live 15:30 prompt ignores that flag), so the
  planner builds the same 7-field row the stream documents use (`stream_candidates._calibration_fields`). Then only a
  row whose multiplier, notional and drop disagree is withheld. (An intermediate version of this work dropped the
  filter; the Copilot review commit on this branch restored it correctly and that approach is kept.)
- **Errors never echo payload content.** `market_data_invalid` carries only the exception type name.
- **`backup_planner.pyz universe`** prints the buyable symbols, count and universe hash from the packaged config.
  The generated prompts contain no stock names; a test fails if any appears, and none mentions Yahoo.
- Yahoo is never required: it exists only as the stream code's optional fallback block, which the backup does not use.

## Amendment: stand down before the broker pull (2026-10-25)

Status: accepted, implemented in the backup prompts and the served procedure. The tests came first.

**Problem.** Today the procedure does STEP 1 gates, then STEP 2 (account lookup, the full seven-day paginated
`get_equity_orders` pull, the published plan read), and only reaches the Mac check in STEP 3. On a normal day the
Claude slot has already succeeded, so every backup fire pays for the procedure fetch, the account lookup, the
order pull and the published read just to end as `stood_down_local_active`. Tool output re-read on each step drives
the cost, not the instruction text. The operator's target is at most 1,000 Perplexity credits per day across the
seven backup fires (see `docs/cost_tracking.md`, "Perplexity backup target band").

**Decision.** Add a stand-down gate between STEP 1 and STEP 2: gates, then `list_devices`, then
`local_heartbeat status`. If the result is `in_progress` or `succeeded`, write the state record and stop, with no
account lookup, no order pull, no published read and no procedure part fetch. Every other outcome goes on to the
existing flow. Stopping early places nothing, so the gate cannot weaken fail-closed behavior.

Answers to the four open questions (operator, 2026-10-25):

1. **Inline in the prompt box, not a new `procedure --part 0`.** The generated prompt runs the gate itself before it
   fetches any procedure part, so a stand-down day makes no procedure call at all. Each prompt must stay under the
   20,000-character box limit (about 9.7 KB was used before; about 12 KB with the gate).
2. **Full-schema state record with nulls.** The early stand-down writes the same STEP 8 record with
   `status: stood_down_local_active` and `run_origin: scheduled_backup`. It fills `trading_day`, `slot`, `task_id`,
   `fired_at_et`, `mac_status`, `mac_path_abandoned`, `routing` and `mac_elapsed_seconds`. It also fills
   `planner_build` and `universe_hash`, which STEP 0 already produced, and `sizing_version` from the prompt header.
   It sets the fields the run never reached (`account_last4`, `plan_source`) to null and the lists
   (`executor_orders`, `orders_planned`, `orders_placed`, `skipped`, `errors`) to `[]`. Readers see one shape.
   Part 3 is never fetched on this path, so the prompt states the record's path and keys inline.
   As before, it sends no notification.
3. **All seven fires, the 10:50 fire (`e028361e`) included.** The procedure is one template, and nothing makes 10:50
   special (Stage 1 above).
4. **The 1,000-credit/day target is recorded in `docs/cost_tracking.md` as an operator target band**, not as a
   measured or estimated figure.

**What does not change.**

- The STEP 1 gate statuses and their stops.
- The `local_status` mapping (off, unreachable, errored, unknown). A probe value that is not recognized still stops
  with `stood_down_local_unknown` and a notification. The early gate runs the same commands as STEP 3a to 3c,
  moved earlier, and STEP 3 reuses their results instead of calling them again.
- The 3-minute Mac budget, which still starts at `list_devices`.
- Hard rules 1 to 11, every act path, the caps and spread checks, the claim/confirm pair and poll 2. Hard rule 2
  still says the account lookup comes "after the step 1 gates"; it now also comes after the stand-down gate, and it
  still precedes any order read or buy, which is what the rule protects.
- **Only `in_progress` and `succeeded` stop early.** Every other result goes on to the procedure unchanged, and
  STEP 3 reuses the gate's `mac_status` and `local_status` instead of probing again. That covers `off`, `errored`,
  `unreachable`, an unknown probe value, a gate status other than PROCEED, and an abandoned Mac path. The
  late-start guard stays where it is in STEP 3c, word for word: it waits 5 minutes, rechecks once and redoes poll 1.
  The `stood_down_local_unknown` and notification path is untouched as well.

**Verification.** Tests assert all of the following:

- In every generated prompt, the gate comes after `gates` and before any `get_equity_orders` call or procedure fetch.
- `in_progress` and `succeeded` stop with `stood_down_local_active`.
- `off` and `errored` continue to the existing flow.
- The late-start guard's line is byte-for-byte unchanged.
- Each prompt stays under 20,000 characters.

The cost effect is measured outside the repo. Take 5 trading days of per-task usage from Perplexity's usage page
before the repaste, then compare 5 shadow days after it, and check each task's model setting. The live tasks are
repasted only after the operator confirms shadow mode.

## Amendment: read the slot-status signal first (2026-10-30)

Status: accepted by the operator; the tests came first and were approved before the code. Not live until the six
tasks are repasted.

**Problem.** With the 2026-10-25 stand-down gate live, the backups still cost about 2,500 Perplexity credits a
trading day; the new target is under 200 (`docs/cost_tracking.md`). On a normal day every fire still:
- ingested a ~12 KB prompt;
- ran `--build-info`, `universe` and `gates`;
- listed devices;
- ran a whole Mac sub-agent for `local_heartbeat status`.

All of that only to stand down.

**Decision.**
1. **The primary publishes a signal.** It is a small public document (`scripts/slot_status.py`, written by
   `local_heartbeat start` / `finish` to the `slot-status` branch). It holds the day, open or closed, and each
   slot's status and time.
2. **The pasted prompt reads it first (STEP A).** It ends the fire, with no other tool call, file or notification,
   only on a slot marked `succeeded` today or a closed market. Every other case goes to STEP B: missing,
   unreadable, another day, `in_progress`, `failed`, or no entry for the slot.
3. **STEP B checks the build stamp, then fetches `procedure --part 0`.** Part 0 is the hard rules, calendar,
   step 0 and the 2026-10-25 stand-down gate, word for word, served by the stamped planner. Parts 1-3 are
   unchanged. Part 1 now needs the token part 0 prints.

**Accepted trade-offs.**
- **The hard rules are no longer pasted.** They still bind every broker step: the pasted prompt names no broker or
  Mac tool, and part 1 cannot be fetched without part 0's token. `content_sha256` covers the rule text.
- **A STEP A stand-down writes no Perplexity state record.** The primary's own artifacts and the status file are
  the record of a normal day.
- **The status file is public.** It reveals only that a slot ran, and when.
- **A false `succeeded` can only cause a missed backup.** It requires write access to the repository.
- **`in_progress` never stands down at STEP A.** A run still going 20 minutes after its slot may have crashed, so
  the existing Mac probe judges it.

**Rollback.** Repaste the previous prompts with the planner build they name, or set `"enabled": false` in
`config/slot_status.json`. With publishing off, every fire takes STEP B and behaves as before this amendment.
